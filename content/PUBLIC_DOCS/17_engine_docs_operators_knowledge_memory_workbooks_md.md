# Knowledge, Memory and Evidence

Last reviewed: 2026-10-16

Public-safe capability guide. The memory discussion covers the implemented
session-recall path; it does not establish general real-user memory or a
learning-promotion permission.

## Knowledge and memory have different sources

Knowledge retrieval selects from configured, authorised sources. Session memory
retains bounded conversation-derived evidence, including compacted history and
attributable corrections. Neither source acquires instruction or execution
authority merely by appearing in context. Availability and permissions still
depend on the selected workflow.

## Engine-managed session recall

The Engine manages the sequence:

1. Retain session records within storage and retention limits.
2. Restrict eligible fragments to the relevant scope.
3. Rank and assemble a bounded recall selection.
4. Admit evidence alongside the task and other context under runtime limits.
5. Record available provider-submission evidence separately from preparation.

Retention and retrieval are separate. Session records can survive a planned
worker rotation without giving the model a database-browsing tool. The storage
adapter may load or scan eligible records; the model receives the context
admitted by the Engine. This is not a claim that every other memory system
provides unrestricted model access.

## Memory Atlas in Sense

Memory Atlas is a read-only projection of retained session records. Select a
session and turn to inspect saved fragments, recorded recall selection, source
references, correction evidence, recorded model identity and available exact
block-delivery checks. The graph and list present the same evidence domain.

A saved snapshot is evidence of the captured record, not necessarily current
live residency. A graph connection describes a retained relationship; it does
not manufacture authoritative semantic facts. Missing source content or absent
delivery checks remain evidence gaps.
Model delivery covers the selected actor request. Delivery to Observer's
separate opinion model is not instrumented by Atlas in this version.

For a fictional example, Harbour's original reference might be HARBOR-314.
An attributable user correction changes it to HARBOR-620. A later question
can select the correction for recall. That selection alone does not establish
admission or submission, and the correction is about Harbour rather than a
general user preference.

## Recall research and report interpretation

Observer supports isolated delivery-method comparisons grouped under a logical
parent. Planned process handoffs retain the same logical child and its session
memory. Separate sessions do not establish provider-cache erasure.

Read feature configuration, recorded execution and model results separately:

- Prepared context is not confirmed provider submission.
- Correct probe answers do not prove exclusive recall dependence.
- Recognized runtime receipts can establish observed compaction, request
  preparation, evaluated safeguards or adaptive-memory adjustments.
- Configured options, unknown receipts and untriggered growth do not establish
  that a feature was exercised.
- Engine memory accounting is distinct from database file size or process RAM.

A controlled twelve-arm run completed with retained rotation and request
evidence; response compliance varied by delivery method. A newer Native only
versus Native with Simplified preparation study has a hundred turns per
isolated governed arm (200 turns total) and is prepared locally. This new study
has no live results yet; its live validation remains pending. Mandatory
safeguards and resource admission remain authoritative.

Private reports retain source and response detail for authorised inspection.
Public projections omit private prompts, retained memory text, operational
identifiers and private diagnostic payloads. This website uses fictional data.

## User memory, NNLSL and workbooks

The session feature does not establish a production user profile across
conversations. Synthetic-user memory experiments are separately scoped research.
Production user memory requires ownership, explicit consent and retention,
correction and deletion standards before availability is claimed.

NNLSL is a separate existing non-neural learning research subsystem. Recall
does not train it, and Atlas does not automatically promote retained notes
into learning. A future integration needs explicit permission, learning
standards and independently validated promotion controls.

Workbook typing, mapping and broader administrative editing workflows remain
outside the verified scope of this guide. Memory Atlas itself does not add
memory-editing, deletion or learning controls.
