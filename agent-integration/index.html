External Agent Integration

Delegated OAuth/MCP connections, human-reviewed task plans, external work evidence and one permission-scoped Project Board, with synthetic demonstrations kept separate.

ExploreEngineering evidence ↗

Connection, approval and execution

Delegated Agent identity

External assistants retain their own inference provider. OAuth consent binds a distinct Agent and registered client to a delegated scope. Expiry, suspension, revocation and current permission checks can stop supported operations. Connection consent is not task approval.

Externally performed work

Agents propose structured task plans for human review, report progress and submit evidence. Approval binds the exact reviewed tasks and revision. Work reports remain Agent claims about external work, not server-observed execution.

Separate synthetic research

Synthetic research retains its own governed step and execution boundaries. External task approval does not create a synthetic execution lease or enable wider Research adapters. Client compatibility and end-to-end acceptance require their own evidence.

Human review from proposal to closure

Exact tasks, current revision

Selecting tasks in an MCP App is not approval. A human authenticates and authorises the specific decision against the current plan. Added work needs fresh approval while earlier approvals and evidence remain retained.

Reported work and acceptance

Task stages distinguish pending approval, reported progress, completed work and human acceptance. Review & sign-off brings completion criteria and evidence together. A progress bar describes reported work, not independently observed execution or accepted results.

Closure is another decision

Acceptance, permission for an Agent to close, and actual closure remain separately recorded. Delegated closure requires current human authorisation, accepted work and a final Agent closing comment. Existing owner/admin lifecycle controls retain their own checks.

Recovery without repeating decisions

Locally prepared widget recovery puts errors and reconnection beside review actions, retains notes and checks saved outcomes after uncertain responses. Reconnection does not repeat approval or restore revoked authority. The reported live interruption still needs deployed human validation.

One workspace, module-owned permissions

Super Admin, Admin and User accounts share the same routes, page components and navigation. Each supported module owns its saved feature and resource grants. Assignment enables eligibility; suspension preserves those grants while preventing access.

Scope before presentation

Backend reads constrain records and fields before rendering or serialisation, including lists, counts, filters, links and evidence. Mutation controls appear only with write authority; direct mutation requests are checked independently.

Read-only access Preview

Administrators can inspect supported screens using the selected account’s current grants. Preview shares signed-in data checks and remains read only. It does not verify password or OTP sign-in or grant permission to act as that account.

Projects and ticket hierarchy

Project membership and parent/sub-ticket links organise work. Each ticket retains its own approvals, evidence, acceptance and lifecycle. Relating tickets does not transfer execution or closure authority.

Current Project Board and public demonstration

Reviewed 18 November 2026 against repository records. Engine 0.2.11 remains the development line; 0.3.0 requires the agreed end-to-end Agent workflows and deployed acceptance. Read the dated technical record.

Shared ticket presentation

Responsive Grid/List views use shared ticket details and preserve queue filters and position. They distinguish Agent-reported progress from human acceptance. Local refinements add on-demand title, description and Project editing with existing permission checks.

Advisory priorities

Agent priority suggestions and dependencies remain separate from human-assigned priority. Audited review does not grant task approval, execution or closure authority. Latest controls require deployment, connector refresh and acceptance.

Fictional demonstrations

The public demo uses fictional tickets, simulated review and sample reports. It demonstrates workflow and presentation, not live permission changes or successful external execution. Explore the fictional Project Board ↗.
